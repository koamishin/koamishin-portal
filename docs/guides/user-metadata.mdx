# Application user metadata

Application metadata adds custom JSON values to a user within one application and environment. For example, the same person can have a different language preference in development and production, or in two applications. Metadata does not require adding a database column for each key.

Each user has two objects per application environment:

| Object | Where it can be read | Example |
| --- | --- | --- |
| `public` | Userinfo with the `metadata:public` user scope, application webhooks, and the management API | Display preferences |
| `private` | The management API with `metadata:read` | Internal integration identifiers |

Private metadata is access-controlled by the management credential; it is **not encrypted at the application layer**. Protect database backups, management credentials, logs, and any consumers of the API. Do not put passwords, API keys, or bearer tokens in metadata. Validate values in your own application and do not treat user-supplied metadata as authorization.

The older `users.metadata` field in the Portal admin panel is a separate, global user field. It is not copied automatically into application metadata and is not returned by the scoped userinfo or webhook payloads. Plan an explicit, reviewed migration if existing applications rely on those values.

## 1. Prepare the application and user

Create an organization and application in the Portal, and enroll the user in both the organization and the application's selected environment. The management credential and the user's OAuth client must be associated with the same environment. The Dashboard's **Quick Add User** and **Import Users** actions can enroll users into the current application; see [tenancy and OAuth](core-concepts.mdx).

Create a separate server-to-server credential on the Portal host. Replace `42` with your application ID and choose the environment. This example grants user reads and both metadata scopes:

```bash
php artisan koamishin:management-client 42 development \
  --scope=users:read --scope=metadata:read --scope=metadata:write \
  --no-interaction
```

Copy the client ID and secret into a secure secret store; the secret is shown only at creation. Keep these credentials on your server and separate from the user's authorization-code client. `metadata:read` permits reading both objects; updates require both `metadata:read` and `metadata:write`, because the response contains both objects. Grant only the scopes the service needs.

## 2. Configure the Laravel SDK

After installing the PHP SDK, set these values in the consuming Laravel application's server-side environment:

```dotenv
KOAMISHIN_PORTAL_URL=https://auth.example.com
KOAMISHIN_MANAGEMENT_CLIENT_ID=your-management-client-id
KOAMISHIN_MANAGEMENT_CLIENT_SECRET=your-management-client-secret
```

Use the client to set and retrieve values. The ID is the Portal user ID returned by the SDK or userinfo:

```php
use Koamishin\Auth\KoamishinManagementClient;

$management = app(KoamishinManagementClient::class);

$metadata = $management->updateUserMetadata(
    id: $userId,
    public: ['preferred_language' => 'en', 'time_zone' => 'Asia/Manila'],
    private: ['billing_customer_id' => 'customer_123'],
);

$metadata = $management->getUserMetadata($userId);
$language = $metadata['public']['preferred_language'] ?? 'en';
```

Each supplied object **replaces that entire object**. An omitted argument leaves the corresponding object unchanged; an empty array clears it. Read and merge existing keys before updating if you intend to preserve them. Concurrent read-modify-write operations can still overwrite each other, so coordinate writers. JSON objects can contain nested JSON values; the combined serialized `public` and `private` objects and the request body are each limited to 16 KiB. SDK and Portal validation errors should be handled by the calling application.

## 3. Read public values for the signed-in user

The PHP SDK requests `metadata:public` by default. Once the user has completed the OAuth flow, the SDK's `KoamishinUser` exposes `publicMetadata`:

```php
use Koamishin\Auth\Facades\Koamishin;

$user = Koamishin::user();
$language = $user?->publicMetadata['preferred_language'] ?? 'en';
```

The Portal returns public metadata in `/api/oauth/userinfo` only when the user token includes `metadata:public`. Private metadata is never included in userinfo. The authenticated user must still be a member of the organization and application environment at the time userinfo is requested.

## Use the HTTP API directly

A backend can request a Passport client-credentials token from `/oauth/token` with the management client ID, secret, and the scopes needed for its request. Send the resulting access token as a Bearer token to the Portal over HTTPS. For example, after securely obtaining a token with `metadata:read metadata:write`:

```bash
curl --fail-with-body --silent --show-error \
  --request PATCH \
  --header 'Accept: application/json' \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer ${MANAGEMENT_ACCESS_TOKEN}" \
  --data '{"public":{"preferred_language":"en"},"private":{"billing_customer_id":"customer_123"}}' \
  "${PORTAL_URL}/api/v1/users/${USER_ID}/metadata"
```

The response is `{ "data": { "public": { ... }, "private": { ... } } }`. Use `GET /api/v1/users/{id}/metadata` with `metadata:read` to retrieve it. An absent or inaccessible user returns 404; a missing grant or scope returns 403. Tokens are bound to the credential's application environment, so a user enrolled only in a different environment is not accessible through it.

## React to metadata changes

Create a webhook endpoint for the same application environment and subscribe to `user.updated`. A successful metadata change queues this event after the transaction commits. The payload includes that environment's public metadata and excludes private and legacy global metadata. Verify the signature over the raw request body and make the handler idempotent; see [webhooks](core-concepts.mdx#webhooks) and the [PHP SDK guide](laravel-sdk.mdx).
