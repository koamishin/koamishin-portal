# Tenancy, OAuth, and webhooks

A Portal organization contains applications. Each application has development and production configurations, separate OAuth clients, and separate application memberships. A person can belong to several organizations or applications, while retaining one underlying Portal user account.

## Create an application

1. Sign in to the admin panel as a super administrator and select an organization.
2. Under **Applications**, create an application. Choose its framework and initial environment, and enter the exact callback URL used by the consuming application. Production callback URLs must use HTTPS.
3. Save both environments' client IDs and any displayed client secrets immediately. Secrets are shown once; store confidential client secrets on the server. A browser client is public and has no secret.
4. Edit the other environment before using it: its callback list starts empty. Switching environments selects that environment's client and callbacks; it does not copy users or metadata into it. The dashboard selection is stored on the application record, so administrators changing the same application can change each other's selected context.
5. Enroll each user in both the organization and the relevant application environment. The Dashboard's **Quick Add User** and **Import Users** actions can attach users to the active application and chosen environment. An account created elsewhere is not automatically enrolled in every application.

Laravel and Node.js applications receive confidential authorization-code clients. The browser-oriented framework selections receive public authorization-code clients. Both use the authorization-code flow; use PKCE for browser integrations. An OAuth client created separately with `passport:client` is not automatically bound to an application environment and is denied by the scoped authorization flow until provisioned and mapped correctly.

For a Laravel consuming application, continue with [the PHP SDK guide](laravel-sdk.mdx). A generated application snippet is a starting point; use an SDK version containing the features described here and test the entire flow.

## Authorization and claims

A mapped OAuth client must identify exactly one active application environment. During authorization and userinfo requests, the Portal checks the organization membership and the application membership for that environment. Banned users and revoked clients are denied. Userinfo also checks current access, so removing a membership prevents subsequent userinfo requests.

| User scope | Optional userinfo claims |
| --- | --- |
| `profile` | Name, username, picture, and update time |
| `email` | Email and verification status |
| `phone` | Phone number and verification status |
| `wallet` | Wallet address |
| `roles` | The user's application-environment membership role; the current permissions list is empty |
| `metadata:public` | Public metadata for this application environment |

`sub`, organization ID, application ID, and environment identify the context. Private metadata and the older global `users.metadata` field are not returned. The Portal's userinfo endpoints are `GET /api/oauth/userinfo` and `GET /api/user`; both now return the scoped claims shape rather than a raw user model. See [application user metadata](user-metadata.mdx) for writing and reading custom values.

These protections apply to the documented OAuth, management API, and webhook flows. They do not create separate databases or automatically scope every administrative feature. The admin panel currently grants global access to `super_admin`; review privileges, all other endpoints, and your deployment before hosting mutually untrusted organizations. A tenant domain is a record and does not provision DNS or TLS. Environment settings for sign-up, MFA, email verification, and session lifetime are not by themselves enforcement guarantees.

The Portal advertises discovery and JWKS endpoints, but does not currently issue OpenID Connect ID tokens or validate OIDC nonces. Treat this integration as OAuth 2.0 with userinfo, not as a complete OIDC provider.

## Server-to-server management

Management credentials are separate Passport client-credentials clients bound to one application environment. Provision them on the Portal host with `php artisan koamishin:management-client`, granting only the scopes required by that service. The API reads users, metadata, and application-scoped OAuth grants for the bound environment; it cannot use that credential to administer unrelated organizations. See the [Laravel SDK guide](laravel-sdk.mdx) and [API reference](../reference/examples.mdx).

## Webhooks

In **Webhook Endpoints**, select an application environment, receiving URL, signature format, and events. Enable the endpoint and subscribe to `user.created`, `user.updated`, and/or `user.deleted`. A subscriber receives events only for enrolled users in its assigned environment. `user.created` is emitted when the supported enrollment workflows attach a user; it is not a general notification for every account created elsewhere. `user.updated` includes basic profile details and that environment's public metadata; `user.deleted` contains the user ID. Private metadata, global metadata, and global roles are not included.

Delivery is queued after a successful transaction, so run and supervise a queue worker. A delivery attempt includes `svix-id`, `svix-timestamp`, and `svix-signature`. Standard-format deliveries also include matching `webhook-id`, `webhook-timestamp`, and `webhook-signature` headers. Verify the timestamp and HMAC-SHA256 signature over the exact raw body before using it. Retries keep the same message ID; consumers must make effects idempotent. Delivery records can contain user data, so restrict access and set a retention policy.

Select the same signature format at both ends:

- **Legacy Koamishin:** the entire configured secret is the HMAC key. Existing endpoints retain this format on upgrade.
- **Standard Webhooks:** the secret is `whsec_` followed by a base64-encoded key of at least 16 bytes; the decoded key signs the payload. The Portal generates a suitable key when creating an endpoint without one.

An endpoint left unassigned after migration receives no user events. Assign it to the intended application environment in the admin panel before resuming delivery. Pending old, unscoped user-event jobs are discarded to prevent cross-application data disclosure. A queued event is also discarded if its endpoint is disabled or reassigned to another environment before delivery. The [SDK guide](laravel-sdk.mdx) includes receiver examples and replay-handling limitations.
