# Deployment and operations

This guide deploys the Laravel application to a server with PHP-FPM and a web server. You can use another host or Octane, but you must adapt and verify its process, storage, and proxy configuration. The [Astro landing and documentation](landing.mdx) are built and hosted separately.

Review [tenancy and OAuth integration](core-concepts.mdx) before connecting real users: application-environment checks cover the documented OAuth, management, and webhook flows, while other Portal features are not automatically tenant-isolated. The advertised OpenID Connect endpoints do not implement the complete OIDC flow. Plan a staging deployment and validate the security and integration behavior needed by your applications before exposing the service.

## 1. Prepare the host

- Provision PHP 8.5, Composer 2, Node.js 22.18 or later in the Node 22 series, and npm. The root frontend build's Vite Plus dependency also supports Node 20.19+ and Node 24.11+, but not every intervening release. Install the PHP extensions required by the locked Composer dependencies and the driver for your database. The frontend build requires PHP because it generates Wayfinder routes.
- Provision a database, a mail transport, and a queue backend. The default `.env.example` uses SQLite and database-backed queues, sessions, and cache; configure alternatives if required. Use private networking and credentials for shared services.
- Create a DNS name and an HTTPS endpoint, for example `auth.example.com`. Configure the web server to serve only the Laravel `public/` directory, or put the app behind a correctly configured TLS-terminating proxy. Do not expose the project root, `.env`, `storage/`, or Passport private key.
- Make `storage/` and `bootstrap/cache/` writable by the application process. Persist `storage/` across releases, including uploads and Passport keys. Protect it from public access except for the intended `public/storage` link. Share the same key material and compatible storage with all instances.

The web server, worker, and deployment commands must use the same application configuration. Set up access restrictions so only an administrator can reach a new deployment until initialization is complete.

## 2. Configure a fresh installation

From a fresh checkout on the deployment host or build machine, install the production PHP dependencies and create an environment file if one does not already exist:

```bash
composer install --no-dev --optimize-autoloader --no-interaction
test -f .env || cp .env.example .env
```

Edit `.env` privately. The following illustrates the settings to review; replace every example with values for your host and provision the corresponding services first:

```dotenv
APP_NAME="Koamishin Portal"
APP_ENV=production
APP_DEBUG=false
APP_URL=https://auth.example.com

DB_CONNECTION=pgsql
DB_HOST=database.internal
DB_PORT=5432
DB_DATABASE=koamishin_portal
DB_USERNAME=portal
DB_PASSWORD=replace-with-a-secret

SESSION_DRIVER=database
CACHE_STORE=database
QUEUE_CONNECTION=database

MAIL_MAILER=smtp
MAIL_HOST=mail.internal
MAIL_PORT=587
MAIL_USERNAME=replace-with-a-username
MAIL_PASSWORD=replace-with-a-secret
MAIL_FROM_ADDRESS=portal@example.com
MAIL_FROM_NAME="${APP_NAME}"
```

Use the mail provider's required scheme and authentication settings. Configure trusted proxies and secure cookies for your actual topology; check generated HTTPS links and passkeys using the public `APP_URL`. See [configuration](../getting-started/configuration.mdx) for the available service settings. Never commit `.env` or put secrets in the Astro build.

Generate the Laravel application key **once for a new instance**:

```bash
php artisan key:generate --no-interaction
```

Keep `APP_KEY` secret, back it up, and keep it stable across releases and all application and worker instances. Changing it can invalidate encrypted data and sessions. Do not run this command during a routine update or when restoring an existing installation.

## 3. Build and initialize the application

Install the locked frontend dependencies, including development dependencies, and build the assets. Then apply the application and enabled module migrations and create the public storage link:

```bash
npm ci
npm run build
php artisan migrate --force --no-interaction
php artisan module:migrate --all --force --no-interaction
php artisan storage:link --no-interaction
php artisan optimize --no-interaction
```

The root `npm run build` generates Wayfinder routes before compiling assets into `public/build/`. Deploy those assets with the matching code and PHP dependencies. `module:migrate` applies enabled module migrations; Blog is enabled in the committed `modules_statuses.json`. If the storage link already exists, verify that it points to the persistent `storage/app/public` directory rather than replacing it blindly.

Do **not** use `composer run setup` for a production installation. It regenerates `APP_KEY` and runs the default seeder, which creates known-password accounts, including a super administrator. See [installation](../getting-started/installation.mdx) for details.

## 4. Start services and create the first administrator

1. Start PHP-FPM and the web server with the document root set to the release's `public/` directory. Configure TLS and proxy headers for your host. The [Laravel deployment guide](https://laravel.com/docs/13.x/deployment) contains a web-server configuration example.
2. While access is restricted, open `https://auth.example.com/setup` using your actual domain. Enter the instance name and a strong, unique administrator password. The wizard creates a `super_admin` and signs that user into `/admin`.
3. Confirm that `storage/oauth-private.key` and `storage/oauth-public.key` both exist, that the application can read them, and that the private key is not publicly accessible. On a fresh install the wizard generates them when the public key is absent. If only one key is present on an existing installation, restore the pair before opening the wizard: it invokes `passport:keys --force` when the public key is missing and can overwrite the private key.
4. Start a supervised queue worker with the same environment and code as the application. For example, run the following command under your process manager and configure it to restart after exit:

    ```bash
    php artisan queue:work --tries=3 --timeout=60 --no-interaction
    ```

5. Confirm the `/up` endpoint responds, sign in to the admin panel, and test email delivery and the relevant authentication flow. `/up` checks that Laravel can respond; it does not replace checks for the database, queue, mail, or connected applications. Remove the temporary access restriction only when your validation is complete.

The wizard is available whenever no user has the `super_admin` role. Keep a secured super administrator and control who can manage roles, because removing the last one reopens setup.

The example worker timeout assumes the default database or Redis `retry_after` of 90 seconds. The worker or per-job timeout must be several seconds shorter than the queue's retry interval to avoid the same job being processed twice. Install PHP's PCNTL extension for worker timeouts and adjust the values to suit your jobs; see the [Laravel queue documentation](https://laravel.com/docs/13.x/queues#job-expirations-and-timeouts). Webhook delivery is queued and needs a running worker.

If your deployment uses scheduled tasks, run `php artisan schedule:run --no-interaction` every minute through your host's scheduler. Monitor application logs, failed jobs, worker availability, disk usage, mail, and backups.

## 5. Deploy an update

1. Back up the database, persistent files, `APP_KEY`, and both Passport keys. Test restoration separately and plan a rollback, especially for irreversible migrations.
2. Deploy the new code, locked Composer dependencies, and matching built assets. Preserve the existing environment file and persistent storage; do not regenerate keys or run the default seeder.
3. Apply migrations and refresh caches:

    ```bash
    php artisan migrate --force --no-interaction
    php artisan module:migrate --all --force --no-interaction
    php artisan optimize:clear --no-interaction
    php artisan optimize --no-interaction
    php artisan queue:restart --no-interaction
    ```

4. Restart or reload long-running application processes as appropriate for your host. If using Octane, reload its workers after deploying code and configuration. Ensure the process manager restarts the queue workers after `queue:restart`.
5. Check `/up`, sign in, and verify the affected integration and queue jobs. Keep the database and storage backups needed by your rollback plan.

Test this release sequence in staging. Laravel caches configuration, so rebuild caches and restart long-running processes when environment values change. Keep secrets and backups access-controlled, and rehearse restoration of the database, uploaded files, `APP_KEY`, and Passport keys together.

## Upgrade an existing integration to scoped access

This release changes authentication and webhook behavior. Test the upgrade in staging with a database backup and a representative connected application before applying it to production:

1. Inventory each application's OAuth client and its intended development or production environment. The migration backfills a legacy selected-environment client only when the existing mapping is unambiguous. Conflicting, duplicate, missing, or unmapped clients remain denied; inspect and repair them deliberately before enabling traffic. Do not map one OAuth client to multiple application environments.
2. Confirm that every intended user belongs to the organization and the correct application environment. Existing accounts are not automatically enrolled in every environment. Use the Dashboard import workflow with **Update details if user email already exists** disabled, or use a scoped management credential with `memberships:write` to enroll existing organization members. Check that the user IDs and target environment are correct first.
3. Update each Laravel consumer to an SDK version containing these changes, configure `KOAMISHIN_APPLICATION_ID` and `KOAMISHIN_ENVIRONMENT`, and test login, refresh, and membership removal. The `/api/user` response is now the same scope-filtered userinfo shape as `/api/oauth/userinfo`, rather than the raw user model. Ensure other clients handle the new claims before deploying.
4. Legacy global `users.metadata` is no longer returned by userinfo or webhooks. Decide which values belong in each application environment, validate them, and migrate them explicitly using the management API; private and public metadata are separate objects.
5. Assign every existing webhook endpoint to its intended application environment. Unassigned endpoints receive no user events. Legacy signing remains the default, but the scoped payload shape changes and already-queued unscoped user events are discarded. Update and test receivers and their idempotency handling before restarting workers.
6. Create separate least-privilege management credentials for services that need the management API, and store the one-time secrets securely. Check userinfo, management access, webhook delivery, and token revocation in each environment.

The migration does not establish tenant isolation for unrelated Portal features. See [tenancy and OAuth](core-concepts.mdx) for the precise boundaries and [Laravel SDK integration](laravel-sdk.mdx) for configuration.

## Bundled containers

`docker-compose.yml` defines an Octane/FrankenPHP portal, queue worker, PostgreSQL 17, Redis, and persistent volumes. It does not run migrations or a scheduler, and its default application key and database password are placeholders. Supply unique secrets and consistent application, mail, and URL configuration to every service.

Treat the Docker configuration as a starting point rather than a production-ready deployment. There is no `.dockerignore`, and the Dockerfile copies its build context, so local `.env`, keys, and other sensitive files can enter image layers. Exclude them before building. The startup script checks `/var/www/html` while the image uses `/app`; the health check uses `ROOT` although the Dockerfile declares it only as a build argument. The Compose worker supplies an explicit command, bypassing the startup script, and its default `--timeout=90` equals the default Redis retry interval. Correct and validate these assumptions, worker settings, storage, migrations, networking, and health checks before exposure. Horizon and Pulse are not installed dependencies.

The workflows in `.github/workflows/` cover CI and release automation. Review their triggers, permissions, registry configuration, and secrets before enabling them in your repository.
