# Centralized login for two Laravel applications

This walkthrough connects two Laravel applications to one Koamishin Portal. App A starts a contextual registration flow, the Portal creates the account, and OAuth returns the user to App A. App B can then authenticate the same Portal account through its own client. Each app keeps its own local session, application membership, and metadata.

Self-service access is controlled by the selected environment's **Allow self-service signup** setting. When it is enabled, a new account can join that environment during signup, and an existing Portal user can join another application after approving its authorization request. When the setting is missing or false, an administrator must enroll the user first. Creating a global account directly at the Portal's generic `/register` page does not choose an application or grant application access.

## Before you start

Complete [Portal installation](installation.mdx), including `/setup`. The local test environment uses these development-only origins:

| Service | Origin                         | Callback                                         |
| ------- | ------------------------------ | ------------------------------------------------ |
| Portal  | `http://portal.localhost:8120` | —                                                |
| App A   | `http://app-a.localhost:8121`  | `http://app-a.localhost:8121/koamishin/callback` |
| App B   | `http://app-b.localhost:8122`  | `http://app-b.localhost:8122/koamishin/callback` |

Make sure all three hostnames resolve to the machine running the servers. Separate hostnames and host-only cookies keep session and CSRF cookies from different apps from interfering. Use HTTPS and your actual domains in production.

For the existing development harness in `~/koamishin-sso-test`, `./run-sso-test.sh start` starts these three servers. Its Portal process uses the isolated `database/sso-test.sqlite` database, not the Portal's normal database. Starting a separate Portal server against the normal database will not find the harness's applications and credentials. Review setup/reset scripts before using them: they are test helpers that can replace test accounts, clients, memberships, and metadata.

For your own local instance, configure its Portal origin and session settings before starting the server:

```dotenv
APP_URL=http://portal.localhost:8120
SESSION_COOKIE=koamishin_portal_session
SESSION_DOMAIN=null
MAIL_MAILER=log
```

`MAIL_MAILER=log` is for local testing. Verification messages and their links are written to `storage/logs/laravel.log`; configure a real mail transport for production. Use a separate browser profile for the administrator and the test user so their Portal sessions do not replace each other.

## 1. Configure the applications and signup policy

In the Portal admin panel, select an organization and create **App A** and **App B** separately:

| Setting                   | App A                                            | App B                                            |
| ------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| Framework                 | Laravel                                          | Laravel                                          |
| Environment               | Development                                      | Development                                      |
| Callback URL              | `http://app-a.localhost:8121/koamishin/callback` | `http://app-b.localhost:8122/koamishin/callback` |
| Allow self-service signup | On for this walkthrough                          | On for this walkthrough                          |

Save each development client ID, one-time secret, and numeric application ID. The application's Laravel environment snippet includes `KOAMISHIN_APPLICATION_ID`. Register the exact callback; a different host, port, or path is a different callback. The Portal validates the client and callback before displaying contextual login or registration.

To change an existing environment's policy, edit the application, choose that environment, and set **Allow self-service signup**. The stored setting is `tenant_application_environments.settings.allow_signups`; only the JSON boolean `true` enables it. Missing or false values keep self-service access closed. Set this policy deliberately for development and production separately.

Two consumers can intentionally share one Portal application and register both callbacks on one client. They then share the application ID, membership boundary, and metadata. To test independent applications, use separate application IDs and client credentials as shown here.

## 2. Configure the Laravel clients

Use the existing `app-a/` and `app-b/` projects, or create two new Laravel 13 projects:

```bash
composer create-project laravel/laravel app-a '^13.0' --no-interaction
composer create-project laravel/laravel app-b '^13.0' --no-interaction
```

Install an SDK version containing `getRegistrationUrl()` in each app. The repository source can be newer than the stable Composer release. For development, use the updated branch and commit the consuming project's lockfile to pin the resolved revision:

```bash
composer config repositories.koamishin-auth vcs https://github.com/koamishin/auth-php.git
composer require koamishin/auth-php:dev-main
php artisan vendor:publish --tag=koamishin-config --no-interaction
```

Use a reviewed release for production. The local test projects may instead use a Composer path repository pointing to the Portal's `packages/koamishin-auth-php` directory; changes to that source are then available directly to the clients.

Configure App A's `.env` with its own credentials and actual numeric application ID:

```dotenv
APP_URL=http://app-a.localhost:8121
SESSION_COOKIE=app_a_session
SESSION_DOMAIN=null

KOAMISHIN_PORTAL_URL=http://portal.localhost:8120
KOAMISHIN_CLIENT_ID=app-a-development-client-id
KOAMISHIN_CLIENT_SECRET=app-a-development-client-secret
KOAMISHIN_REDIRECT_URI=http://app-a.localhost:8121/koamishin/callback
KOAMISHIN_APPLICATION_ID=app-a-numeric-id
KOAMISHIN_ENVIRONMENT=development
```

Configure App B with its different client and application ID:

```dotenv
APP_URL=http://app-b.localhost:8122
SESSION_COOKIE=app_b_session
SESSION_DOMAIN=null

KOAMISHIN_PORTAL_URL=http://portal.localhost:8120
KOAMISHIN_CLIENT_ID=app-b-development-client-id
KOAMISHIN_CLIENT_SECRET=app-b-development-client-secret
KOAMISHIN_REDIRECT_URI=http://app-b.localhost:8122/koamishin/callback
KOAMISHIN_APPLICATION_ID=app-b-numeric-id
KOAMISHIN_ENVIRONMENT=development
```

Keep secrets out of version control. Ensure each app has its own `APP_KEY` and a ready session store. Rebuild configuration caches after changing `.env`. The SDK checks the returned application ID and environment before accepting the identity.

## 3. Add registration, login, and callback routes

In each app's `config/auth.php`, add this guard inside the existing `guards` array:

```php
'koamishin' => [
    'driver' => 'koamishin',
],
```

Add these routes to each app's `routes/web.php`, avoiding duplicate route names if the app already has authentication routes:

```php
use App\Exceptions\KoamishinIdentityConflict;
use App\Services\KoamishinUserProjector;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Route;
use InvalidArgumentException;
use Koamishin\Auth\Facades\Koamishin;

Route::get('/register', function () {
    return redirect()->away(Koamishin::getRegistrationUrl('/dashboard'));
})->name('register');

Route::get('/login', function () {
    return redirect()->away(Koamishin::getLoginUrl('/dashboard'));
})->name('login');

Route::get('/koamishin/callback', function (Request $request, KoamishinUserProjector $projector) {
    if ($request->query('error')) {
        abort(403, 'Sign-in was not completed.');
    }

    $input = $request->validate([
        'code' => ['required', 'string'],
        'state' => ['required', 'string'],
    ]);

    try {
        $identity = Koamishin::handleCallback($input['code'], $input['state']);
    } catch (InvalidArgumentException $exception) {
        abort(403, 'Invalid or expired sign-in request.');
    }

    try {
        $projector->sync($identity);
    } catch (InvalidArgumentException $exception) {
        Koamishin::logout();

        abort(403, 'The Portal identity does not match this application configuration.');
    } catch (KoamishinIdentityConflict $exception) {
        Koamishin::logout();

        abort(409, $exception->getMessage());
    }

    return redirect()->to(Koamishin::consumeReturnTo('/dashboard'));
});

Route::get('/dashboard', function (Request $request) {
    $identity = $request->user('koamishin');
    $localUser = App\Models\User::query()
        ->where('koamishin_user_id', $identity->id)
        ->firstOrFail();

    return response()->json([
        'id' => $identity->id,
        'local_user_id' => $localUser->id,
        'name' => $localUser->name,
        'email' => $localUser->email,
        'application_id' => $identity->applicationId,
        'environment' => $identity->environment,
        'public_metadata' => $localUser->koamishin_public_metadata,
    ]);
})->middleware('auth:koamishin');

Route::post('/logout', function () {
    Koamishin::logout();

    return redirect('/');
})->name('logout');
```

`getRegistrationUrl()` creates the same session-backed OAuth state and PKCE verifier as login, then adds `screen_hint=signup`. The Portal can therefore display the named application's registration page and resume the original authorization request. A plain redirect to the Portal's generic `/register` page has no originating application context.

The callback receives an authorization code, then the server exchanges it for tokens and fetches the permitted claims. User data and metadata are not placed in the callback URL. The route above projects the verified Portal subject before redirecting. Each app should have a unique `koamishin_user_id` column on its local `users` table. This sample expects the `email` scope and a non-empty email claim, and it mirrors central email verification to Laravel's `email_verified_at`. Store only the profile fields and public metadata that app needs; never store a Portal password or access token in that row. If a local account already has the same email, clear the SDK session and require an explicit trusted linking flow instead of matching by email. See the [SDK projection guide](../guides/laravel-sdk.mdx#maintain-a-local-eloquent-user-projection) for the migration and service.

The SDK guard still returns the central `KoamishinUser`. Resolve the local model explicitly when the app needs its own Eloquent relationships. For example, an app's `User::posts()` relation reads from that app's database; it does not fetch or join data from the Portal. Use the Portal management API for centrally owned data.

Submit logout through a CSRF-protected POST form; it clears the local app's SDK session without ending the Portal's browser session.

## 4. Try signup in App A and login in App B

If using the existing harness, start it with its `start` action. Otherwise run the Portal and clients on the configured ports, each in its own terminal:

```bash
# In the Portal checkout, using the intended development database:
php artisan serve --host=127.0.0.1 --port=8120 --no-interaction
```

```bash
# In app-a/:
php artisan serve --host=127.0.0.1 --port=8121 --no-interaction
```

```bash
# In app-b/:
php artisan serve --host=127.0.0.1 --port=8122 --no-interaction
```

In the test user's browser profile:

1. Open App A's `/register`. The Portal should show App A's name and development environment on its registration page.
2. Create a new account and complete the authorization request. With self-service signup enabled, the Portal enrolls the new account in App A's organization and environment and returns the browser to App A's callback and `/dashboard`.
3. Confirm the user appears in the Portal's central directory and App A's local `users` table with the same `koamishin_user_id`. App A's dashboard should show both the Portal subject and the app's local user ID.
4. Open App B's `/login` in the same browser profile. The Portal can reuse its existing login session. If the user is not enrolled in App B, self-service signup must also be enabled there; approving App B's consent request adds that membership before returning to App B.
5. Compare the dashboards: the Portal user ID should match, while each app has its own local user row and application ID. Each app keeps its own session, app-owned Eloquent relationships, and metadata.

An active Portal login can avoid another password prompt. Authorization consent and application access remain specific to the requesting app.

## 5. Add custom metadata from a trusted backend

New accounts start with empty application metadata. A trusted service can set values using a management credential bound to the appropriate application environment:

```php
use Koamishin\Auth\KoamishinManagementClient;

$management = app(KoamishinManagementClient::class);
$management->updateUserMetadata(
    $portalUserId,
    public: ['theme' => 'dark', 'plan' => 'standard'],
    private: ['internal_customer_id' => 'C-123'],
);
```

Provision the credential with `metadata:read` and `metadata:write`; see [application user metadata](../guides/user-metadata.mdx). Each supplied object replaces its entire bucket. The default SDK user scopes include `metadata:public`, so the next authenticated request can read `publicMetadata`. Private metadata remains available only through authorized management access. App A's metadata is not copied into App B's separate application environment.

## Closed signup and troubleshooting

For an environment with self-service signup disabled, an administrator must enroll the account in both the organization and that application environment. The Dashboard's **Import Users** workflow can attach an existing account; verify its email first and disable **Auto-verify** and **Update details** to preserve its existing credentials and roles. A management client with `memberships:write` can enroll an existing organization member by Portal user ID. See the [API reference](../reference/examples.mdx).

- **Registration opens a generic Portal page:** use `getRegistrationUrl()` and retain the Laravel session through the callback.
- **Signup or joining App B is denied:** check the selected environment's explicit signup policy, memberships, active client, and SDK application/environment configuration.
- **The callback fails:** check the exact registered host, port and path, the client secret, local hostname resolution, and session storage. Start a fresh flow from the app if its state expires.
- **Metadata is empty:** write values through the correct environment's management credential and request `metadata:public`. Global user metadata and private metadata are not userinfo claims.

For session refresh, authorization checks, webhooks, and deployment configuration, see [Laravel SDK integration](../guides/laravel-sdk.mdx). The Portal implements OAuth 2.0 with userinfo and does not issue OIDC ID tokens.
